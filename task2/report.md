## 2.1 Triton

Triton 把"线程调度、同步、流水、指令选择"交给编译器，把"Tile 怎么切、数据放哪、怎么掩码"留给程序员。————Deepseek

### 回答：Triton Program 和 CUDA Block 是什么关系？

| 维度 | CUDA Block | Triton Program |
|---|---|---|
| 语义 | 线程集合，块内每个线程干什么由你写死 | 一块 tile（如 128×128 输出），块级语义 |
| 线程数 | `blockDim`，你指定 | 编译器按 `num_warps` 与 tile 大小决定 |
| 同步 | `__syncthreads()`，你插入 | 自动插入 |
| 抽象层次 | 线程级 | 块级/张量级 |

CUDA Block是一个线程集合，块内每个线程干什么是写死的，抽象层是在软件的线程级，而Triton Program则是一块tile,是一个块，抽象层是块级/张量级

一个 Triton Program 大致对应一个 CUDA Block（ds补充）

## 2的最后一个问题 CUDA vs DSL vs cuBLAS

| 维度 | Task 1 CUDA | Task 2 Triton | cuBLAS / torch.matmul |
|---|---|---|---|
| 代码复杂度 | 高（自己管同步/下标） | 低（GEMM 核心不到 40 行） | 最低（一行 API） |
| 首次编译 | nvcc 秒级 | JIT 需编译（单独记录，不算稳态） | 无 |
| 稳态性能 | 手调 tile/pipeline 才能接近 | `tl.dot` 吃 Tensor Core，调参后明显好于手写 Naive | 最好（专门算法+split-K+CUTLASS 流水） |
| 程序员负责 | 线程映射、shared memory、同步 | Tile 大小、mask、程序数 | 基本不负责 |
| 换 Shape | 重新调参 | autotune（要 Shape key） | 库内自适应，最稳 |

**结论**：DSL 的收益是让编译器接管最容易写错的低层部分（同步、流水、MMA），把程序员时间集中到 tile 与算法结构；但"更快"不是自动的——`BLOCK_*`/`num_warps`/`num_stages` 仍要按 Shape 调，这正是 2.2 C 演示的事。**正确不等于高性能**：比 PyTorch 慢时先看 Timeline、访存和参数配置。
